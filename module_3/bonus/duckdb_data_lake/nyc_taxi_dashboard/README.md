# 🦆 NYC Yellow Taxi · BI-дашборд на DuckDB

DuckDB читає **parquet-файли напряму** (data lake, без ETL і без сервера БД) і віддає запити Dash-дашборду.

```
data/year=2019/month=01/*.parquet ─▶ DuckDB (VIEW + SQL) ─▶ Dash (KPI, графіки, мапа зон)
```

| Файл / папка | Що це |
|---|---|
| `app.py` | дашборд (порт **8055**): фільтри рік / місяць, KPI, інсайти, мапа |
| `download_data.py` | завантажує parquet з NYC TLC у `data/` |
| `data/` | 60 файлів, 2019–2023, ~3 ГБ (**у `.gitignore`**, у git не потрапляє) |
| `taxi_zones/` | shapefile зон для мапи |
| `assets/` | стилі для Dash |

Теорія — [`../duckdb_parquet_datalake.md`](../duckdb_parquet_datalake.md), приклади — ноутбуки `../note_bonus_duckdb_data_lake*.ipynb`.

## Запуск

```bash
pip install duckdb geopandas pyogrio plotly dash dash-bootstrap-components
python download_data.py      # лише якщо data/ порожня
python app.py                # → http://127.0.0.1:8055
```

> **Перший запуск ~30 с**: DuckDB один раз згортає ~200 млн поїздок у компактний «куб»
> (рік × місяць × година × день тижня × зона, ~1,5 млн рядків) і кладе його в `.cache/` (~28 МБ, у `.gitignore`).
> Далі старт швидкий, а клік по фільтру — **~0,3 с**. Змінились файли в `data/` — кеш перебудується сам.

## Чому саме так (для студентів)

- **Матеріалізація агрегатів.** Рахувати `SUM/COUNT` по 200 млн рядків на кожен клік — марно. Згортаємо один раз, далі працюємо з малою таблицею. Середні рахуємо як `SUM / кількість`, тож результат такий самий, як `AVG` по сирих даних.
- **Потоки.** Dash виконує колбеки паралельно, а одне з'єднання DuckDB не потокобезпечне. Тому кожен потік бере свій `con.cursor()` (функція `db()` в `app.py`). Без цього паралельні запити перемішують результати.
