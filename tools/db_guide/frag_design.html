Що таке PostgreSQL, Redis, data lake і колонкове зберігання

Чотири види сховищ відповідають на різні питання. Перш ніж будувати базу, треба знати, як кожне з них зберігає дані, бо звідси випливає, що в ньому робити легко, а що — боляче.

🐘 Реляційна база (PostgreSQL)

Як зберігає: таблиці з рядків і колонок на диску. Кожна таблиця має схему: назви й типи колонок, обов'язковість, перевірки. Рядки різних таблиць пов'язані ключами: orders.restaurant_id → restaurants.id.

Мова: SQL — SELECT … JOIN … WHERE … GROUP BY.

Гарантії: транзакції ACID — записалось або все, або нічого, і назавжди.

Для чого: джерело правди, гроші, довідники, будь-які дані зі зв'язками.

У проєкті: sql/init.sql (схема), app/db.py (запити).

⚡ Сховище ключ → значення в пам'яті (Redis)

Як зберігає: один великий словник у RAM. Ключ — рядок (order:42), значення — структура: рядок, хеш, список, множина, sorted set, stream, geo.

Мова: команди — HSET, INCR, XADD… Кожна атомарна.

Гарантії: швидкість (мікросекунди) й атомарність. Збереження на диск налаштовується (AOF/RDB), але схеми та зв'язків немає.

Для чого: кеш, лічильники, черги, рейтинги, «хто поруч», стан, який ділять кілька процесів.

У проєкті: app/config.py (усі ключі), menu.py, orders.py, dispatcher.py, simulator.py.

🗄️ Data lake

Як зберігає: звичайні файли (parquet, CSV, JSON) у папках або хмарному сховищі, розкладені за датою: data/year=2024/month=05/*.parquet. Сервера бази немає.

Мова: будь-який рушій, що читає файли: DuckDB, Spark, pandas.

Гарантії: дешево зберігати роки історії, її можна читати багатьма інструментами. Окремі рядки не оновлюють: дописують нові файли.

Для чого: архів і аналітика. Шари bronze → silver → gold — від сирого до чистого.

У курсі: module_3/bonus/duckdb_data_lake/, 200 млн поїздок NYC Taxi.

🦆 Колонкове зберігання й DuckDB

Як зберігає: parquet і DuckDB кладуть поруч значення однієї колонки, а не одного рядка. Запит «сума total за районами» читає дві колонки зі ста, і вони добре стискаються.

Мова: SQL, майже як у PostgreSQL, але просто по файлах: FROM 'orders.parquet'.

Гарантії: швидкі агрегати по мільйонах рядків. Не для частих дрібних записів.

Для чого: звіти, дашборди, дослідження даних.

Вкладка «Аналітика»: анімація рядки проти колонок.

Як спроєктувати базу даних: 7 кроків

Базу не починають з CREATE TABLE. Починають з питань, на які система має відповідати, і йдуть зверху вниз: сценарії → сутності → поля → зв'язки → таблиці → гарячі операції в Redis → аналітика. Пройди кроки на «Смачно + Таксі». На кожному показано, що ми вирішили, де це в коді і чому саме там.

🔮 Прогноз: з чого почнеш проєктувати базу для служби доставки — з таблиць чи з питання «що користувачі й сервіси мають робити»?

З питань. Таблиці — відповідь на них. Якщо почати з таблиць, з'являться колонки, які ніхто не читає, і не буде тих, без яких система не працює, наприклад «хто з кур'єрів вільний зараз».

Чек-лист: база зрозуміла, якщо…

  • кожна таблиця — одна сутність, названа іменником у множині (orders), з первинним ключем id;
  • кожен зв'язок — FOREIGN KEY з назвою <сутність>_id; M:N — окрема таблиця-зв'язка;
  • правила даних записані в схемі (NOT NULL, CHECK, UNIQUE), а не лише в коді;
  • гроші — NUMERIC, час — TIMESTAMPTZ;
  • кожен ключ Redis має формат <сутність>:<id> або <група>:<призначення>, усі описані в одному файлі, і в кожного відомо, з якої правди його можна відновити;
  • усе, що тимчасове, має TTL;
  • SQL живе в одному модулі (db.py), ключі — в одному (config.py).
