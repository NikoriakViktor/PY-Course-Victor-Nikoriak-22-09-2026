Історія замовлень: від PostgreSQL до DuckDB

PostgreSQL накопичує завершені замовлення. Рано чи пізно бізнес питає: «Який виторг кожного ресторану? О котрій годині найбільше замовлень? Скільки в середньому їде кур'єр?» Такі запити читають усю історію, але лише кілька колонок. Для них є колонкові аналітичні рушії на кшталт DuckDB. Подивись, скільки даних прочитає кожен підхід.

🔮 Прогноз: запит SELECT restaurant_id, SUM(total) FROM orders GROUP BY restaurant_id. Скільки з шести колонок таблиці йому насправді потрібно? Скільки прочитає PostgreSQL?

Потрібні дві колонки: restaurant_id і total. PostgreSQL зберігає дані рядками: щоб дістати дві колонки, він читає сторінки з цілими рядками, тобто всі шість. DuckDB і parquet зберігають колонками й читають лише дві. На 200 млн рядків це різниця між хвилинами й секундами.

🐘 Рядкове зберігання (PostgreSQL, OLTP) рядок за рядком: зручно вставити чи змінити одне замовлення

🦆 Колонкове зберігання (parquet / DuckDB, OLAP) колонка за колонкою: зручно рахувати по всій історії

🔴 Поглиблення: читати PostgreSQL напряму
У DuckDB є розширення postgres: ATTACH 'postgresql://taxi:taxi@localhost:5434/smachno' AS pg (TYPE postgres), а далі SELECT … FROM pg.orders. Зручно для разових запитів. Але важкі аналітичні запити краще ганяти по копії в parquet, щоб не навантажувати джерело правди.
